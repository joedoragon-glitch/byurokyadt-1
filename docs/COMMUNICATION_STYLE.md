# Public communication style — БЮРОКЯДТ-1

This guide applies to **drafts of forum replies, project updates, release notes and other public writing attributed to the owner**, not in-game Soviet office signage, character voice or marketing authorization. It adapts general communication preferences from the owner's separate game project without reproducing any private writing profile, samples or personal correspondence.

Write like an individual maker sharing a peculiar game and the experience of improving it, **not a studio running a hype campaign**. Use concrete observations, natural paragraphs, occasional dry or gently absurd humor and enough detail to explain what a change means to the player. Avoid forced drama, empty superlatives, promotional slogans, excessive emojis, repetitive headings and corporate language. Give readers the useful result before implementation jargon.

The premise supports a quiet joke: an immense official machine certifying the existence of a document. Do not make every sentence a gag, and do not confuse the author's conversational voice with the fictional ministry's deliberately theatrical written language. The latter belongs **inside the game**; player-facing instructions must still be understandable.

Draft accurately. Distinguish proposed, implemented, tested, merged, published and physically verified. A successful CI job is not proof of authentic Chromebook performance, audible appeal or a live user experience. Do not invent the owner's experiences, emotions, tester observations, quotes, approvals or intended announcements. Match the audience and original thread language; for Spanish-language conversation, prefer natural Latin American Spanish rather than literal translated advertising.

The owner may ask for a copy-ready draft; prepare it without requiring separate permission to write. **Never send or publish it without the owner's explicit authorization.** A repository document does not change a private ChatGPT writing profile or automatically apply to other conversations unless a collaborator reads it.

For accurate release claims, inspect [Development state](DEVELOPMENT_STATE.md), the exact GitHub workflow and live build. For product identity, consult [Creative direction](CREATIVE_DIRECTION.md). This is a working summary, not a quotation or an exhaustive model of the owner's personal writing.
